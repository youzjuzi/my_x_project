# 端口与链接配置说明

本文档按当前代码配置整理项目的端口、服务链接和代理关系。遇到旧 README 或历史注释里的端口不一致时，以本文和对应配置文件为准。

## 1. 总览

| 服务 | 本地开发默认地址 | Docker/部署默认地址 | 配置来源 | 说明 |
|---|---:|---:|---|---|
| 前端 Vite 开发服务 | `http://localhost:8001` | 不使用 Vite，由 Nginx 托管 | `frontend-web/vite.config.ts` | 本地 `npm run dev:*` 使用 |
| 前端 Nginx 静态服务 | 不使用 | `http://localhost:8888` | `docker-compose.yml`、`frontend-web/nginx.conf` | Docker 对外入口，`8888 -> 容器 80` |
| Java 后端 | `http://localhost:9999` | 容器内 `http://backend:9999` | `backend-java/src/main/resources/*.yml`、根目录 `.env` | Docker 中当前未直接暴露给宿主机 |
| Redis | `localhost:6379` | `redis:6379`，同时映射 `localhost:6379` | `application*.yml`、`docker-compose.yml` | Docker 中后端通过服务名 `redis` 访问 |
| MySQL | 通常 `localhost:3306` 或 `.env` 指定 | `.env` 中 `SPRING_DATASOURCE_URL` | `application*.yml`、根目录 `.env` | 生产环境通过环境变量覆盖 |
| AI 识别服务 | `http://127.0.0.1:8080` | 按 AI 机器实际地址 | `ai-server/server/config.py`、`ai-server/.env.example` | `main.py` 实际监听 `AI_WEBRTC_PORT` |

## 2. 本地开发访问方式

### 前端

本地前端由 Vite 启动：

```bash
cd frontend-web
npm run dev:local
```

访问地址：

```text
http://localhost:8001
```

端口配置在 `frontend-web/vite.config.ts`：

```ts
server: {
  host: '0.0.0.0',
  port: 8001
}
```

Tauri 开发模式也依赖这个地址，配置在 `frontend-web/src-tauri/tauri.conf.json`：

```json
"devUrl": "http://localhost:8001"
```

### Java 后端

当前后端端口是 `9999`，不是旧文档中的 `8080`。

访问地址：

```text
http://localhost:9999
http://localhost:9999/swagger-ui/index.html
```

配置来源：

| 文件 | 配置 |
|---|---|
| `backend-java/src/main/resources/application.yml` | `server.port: 9999` |
| `backend-java/src/main/resources/application-dev.yml` | `server.port: 9999` |
| `backend-java/src/main/resources/application-prod.yml` | `server.port: 9999` |
| 根目录 `.env.example` | `SERVER_PORT=9999` |
| 根目录 `.env` | 可覆盖 `SERVER_PORT` |

如果要改后端端口，建议同步修改：

1. 后端 `server.port` 或根目录 `.env` 的 `SERVER_PORT`
2. `frontend-web/vite.config.ts` 中所有代理目标 `http://localhost:9999`
3. `frontend-web/nginx.conf` 中 `proxy_pass http://backend:9999`
4. `backend-java/Dockerfile` 的 `EXPOSE 9999`
5. `docker-compose.yml` 中 `backend.expose`

### 前端到 Java 后端的代理

本地开发时，前端请求并不是直接写死完整后端域名，而是：

```js
baseURL: import.meta.env.VITE_BASE_API
```

在 `frontend-web/.env.dev_local` 中：

```env
VITE_BASE_API = ''
```

这表示前端请求 `/auth/login`、`/user/list` 等同源路径，然后由 Vite 代理转发到 `http://localhost:9999`。

Vite 当前代理路径：

```text
/auth
/captcha
/user
/role
/menu
/profile
/challenge
/questionSet
/questionBank
/sign
/dashboard
```

注意：`frontend-web/src/api/qiniu.js` 里有 `/qiniu/upload/token`，但当前 Vite 代理没有 `/qiniu`，而且后端当前也没有对应 controller；这个接口看起来仍是占位代码。Docker Nginx 配了 `/qiniu` 代理，但后端没有实际接口时仍然不可用。

## 3. Docker 部署访问方式

Docker Compose 当前有三个服务：

| Compose 服务 | 容器名 | 容器内端口 | 宿主机端口 | 访问方式 |
|---|---|---:|---:|---|
| `frontend` | `web-vue3` | `80` | `8888` | 浏览器访问 `http://localhost:8888` |
| `backend` | `x-admin` | `9999` | 未映射 | 只能被 Compose 网络内服务访问 |
| `redis` | `x_redis` | `6379` | `6379` | 宿主机可访问 `localhost:6379` |

启动：

```bash
docker compose up -d --build
```

Docker 模式下推荐访问：

```text
http://localhost:8888
```

此时前端静态资源由 Nginx 提供，接口由 `frontend-web/nginx.conf` 代理到 Java 后端：

```nginx
proxy_pass http://backend:9999;
```

Nginx 代理路径：

```text
/auth
/user
/role
/menu
/profile
/challenge
/questionSet
/questionBank
/captcha
/dashboard
/sign
/qiniu
```

重要：`docker-compose.yml` 里后端只写了 `expose: "9999"`，没有 `ports: "9999:9999"`。所以宿主机不能直接访问 `http://localhost:9999` 里的 Docker 后端，除非你手动加端口映射。正常业务请求应走：

```text
浏览器 -> http://localhost:8888 -> Nginx -> http://backend:9999
```

如果想在 Docker 部署时直接打开 Swagger，需要给后端加端口映射，或在 Nginx 里额外代理 `/swagger-ui` 和 `/v3/api-docs`。

## 4. AI 识别服务链接

AI 服务配置在 `ai-server/server/config.py`：

```py
HOST = os.environ.get("AI_SERVER_HOST", "0.0.0.0")
PORT = int(os.environ.get("AI_SERVER_PORT", "8001"))
WEBRTC_PORT = int(os.environ.get("AI_WEBRTC_PORT", "8080"))
```

但当前 `ai-server/main.py` 实际启动的是：

```py
uvicorn.run(
    "server.app:app",
    host=config.HOST,
    port=config.WEBRTC_PORT,
    reload=False
)
```

所以主入口实际监听的是 `AI_WEBRTC_PORT`，默认 `8080`。`AI_SERVER_PORT=8001` 当前主要是历史/预留配置，不是 `main.py` 的实际监听端口。

AI 服务接口结构：

```text
GET  /health
POST /recognition/webrtc/offer
POST /recognition/webrtc/polish
POST /practice/webrtc/offer
POST /practice/webrtc/polish
POST /challenge/webrtc/offer
POST /challenge/webrtc/polish
```

前端 AI 地址由 `VITE_AI_SERVER_URL` 控制，逻辑在 `frontend-web/src/services/webrtcClient.js`：

```js
const DEFAULT_AI_SERVER_BASE_URL =
  import.meta.env.VITE_AI_SERVER_URL || 'http://127.0.0.1:8002'
```

然后自动拼出：

```text
${VITE_AI_SERVER_URL}/recognition/webrtc/offer
${VITE_AI_SERVER_URL}/practice/webrtc/offer
${VITE_AI_SERVER_URL}/challenge/webrtc/offer
```

当前前端环境文件里 AI 地址如下：

| 文件 | AI 地址 |
|---|---|
| `frontend-web/.env.dev_local` | `http://127.0.0.1:8002` |
| `frontend-web/.env.dev_test` | `http://192.168.5.192:8002` |
| `frontend-web/.env.dev_prod` | `http://192.168.5.192:8002` |
| `frontend-web/.env.dev_cloud` | 云端临时地址 |
| `frontend-web/.env.build_prod` | `http://172.26.112.252:8080` |

这里有一个明显的端口不一致：AI 服务模板默认 `AI_WEBRTC_PORT=8080`，但本地前端默认连 `8002`。如果你本机启动 `python main.py` 且没有设置 `AI_WEBRTC_PORT`，前端应改为：

```env
VITE_AI_SERVER_URL=http://127.0.0.1:8080
```

或者反过来，让 AI 服务监听 `8002`：

```env
AI_WEBRTC_PORT=8002
```

## 5. 外部服务链接

### DeepSeek

Java 后端和 AI 服务各自有一套 LLM 配置。

Java 后端：

| 变量 | 默认值/示例 |
|---|---|
| `AI_DEEPSEEK_API_KEY` | 不写入文档，放根目录 `.env` |
| `AI_DEEPSEEK_URL` | `https://api.deepseek.com/chat/completions` |
| `AI_DEEPSEEK_MODEL` | `deepseek-chat` |

AI 服务：

| 变量 | 默认值/示例 |
|---|---|
| `LLM_API_KEY` | 不写入文档，放 `ai-server/.env` |
| `LLM_BASE_URL` | `https://api.deepseek.com` |
| `LLM_MODEL` | `deepseek-chat` |

### Cloudflare R2

头像上传使用 Cloudflare R2。配置在根目录 `.env`，模板在 `.env.example`：

```env
CLOUDFLARE_R2_ACCESS_KEY=change_me
CLOUDFLARE_R2_SECRET_KEY=change_me
CLOUDFLARE_R2_ENDPOINT=https://your-account-id.r2.cloudflarestorage.com
CLOUDFLARE_R2_BUCKET_NAME=your_bucket_name
CLOUDFLARE_R2_DOMAIN=https://your-avatar-domain.example.com
```

本地开发如果不配置 R2，后端会尽量跳过 Bean 注册；但调用上传头像接口时仍需要可用 R2 配置。

## 6. 常见场景怎么配

### 场景 A：全部本机开发

推荐配置：

```text
前端 Vite: http://localhost:8001
Java 后端: http://localhost:9999
Redis: localhost:6379
MySQL: localhost:3306 或外部数据库
AI 服务: http://127.0.0.1:8080
```

关键点：

1. `frontend-web/.env.dev_local` 的 `VITE_BASE_API` 保持空字符串，让 Vite 代理 Java 后端。
2. `frontend-web/.env.dev_local` 的 `VITE_AI_SERVER_URL` 要和 AI 服务实际端口一致。
3. 如果 AI 用默认配置启动，就填 `http://127.0.0.1:8080`。

### 场景 B：前端本机，后端本机，AI 在另一台机器

推荐配置：

```env
VITE_BASE_API=''
VITE_AI_SERVER_URL=http://AI机器IP:8080
```

AI 机器上的 `ai-server/.env`：

```env
AI_SERVER_HOST=0.0.0.0
AI_WEBRTC_PORT=8080
```

同时确认 AI 机器防火墙放行 `8080`。

### 场景 C：Docker 部署 Web + Java + Redis，AI 单独部署

浏览器访问：

```text
http://服务器IP:8888
```

前端生产构建使用 `frontend-web/.env.build_prod`：

```env
VITE_BASE_API=''
VITE_AI_SERVER_URL=http://AI机器IP:8080
```

Java 后端不需要暴露给公网，Nginx 会在 Compose 网络里访问：

```text
http://backend:9999
```

### 场景 D：需要宿主机直接访问 Docker 后端

在 `docker-compose.yml` 的 `backend` 服务下增加：

```yaml
ports:
  - "9999:9999"
```

然后可以访问：

```text
http://localhost:9999/swagger-ui/index.html
```

## 7. 排查清单

| 现象 | 优先检查 |
|---|---|
| 前端页面打不开 | Vite 是否在 `8001`，或 Docker Nginx 是否在 `8888` |
| 登录接口 Network Error | Java 后端是否在 `9999`，Vite/Nginx 代理是否指向正确 |
| Docker 下 `localhost:9999` 打不开 | 当前 Compose 没映射后端端口，这是正常现象 |
| Docker 下页面能开但接口 404/502 | 看 `frontend-web/nginx.conf` 的代理路径和 `backend:9999` |
| AI 识别连接失败 | `VITE_AI_SERVER_URL` 是否和 `AI_WEBRTC_PORT` 一致 |
| 本地 AI 默认启动后前端连不上 | 前端默认可能连 `8002`，而 AI 默认监听 `8080` |
| Redis 连接失败 | 本地用 `localhost:6379`，Docker 后端用 `redis:6379` |
| Swagger 打不开 | 本地访问 `9999`；Docker 模式需暴露后端端口或增加 Nginx 代理 |

## 8. 当前最建议统一的端口

为减少混乱，建议后续统一成下面这组：

```text
前端开发: 8001
Docker Web 对外: 8888
Java 后端: 9999
Redis: 6379
MySQL: 3306，外部云数据库按实际 URL
AI WebRTC/FastAPI: 8080
```

重点是把所有 `8002` 的 AI 地址改成 `8080`，或者明确把 AI 服务改为监听 `8002`。两边只要统一，识别链路就会清楚很多。
